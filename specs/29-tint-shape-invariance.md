# Tint Shape Invariance

> **Status: draft (not started).** Tinting a sprite/button must never change *which* braille dots are lit — only their color. Confirmed broken: rendering the same `Button` across `Idle`/`Hover`/`Pressed` states produces genuinely different braille glyphs (not just different colors) at multiple cells — e.g. one cell shows `⣻` (7 dots) in Idle, `⢻` (a different 7-dot pattern) in Hover, `⣿` (all 8 dots) in Pressed. The shape of an icon visibly shifts as its button's interaction state changes.

## Purpose
Restore (or establish, if it never actually held) the invariant that color/tint operations are pure colorization — they recolor already-decided pixels and never re-decide which pixels are "on."

## Root Cause
`dots::cell_from_dots` (the braille-glyph decision function) uses an **adaptive per-cell luma threshold**: a dot's bit is set only if its luma is `>=` the average luma of all visible (non-transparent) dots in that 2×4 cell. This threshold is recomputed fresh every time `dots_to_grid` runs — including after `tint()` has already recolored the buffer.

`tint()` is a per-channel multiply (`out = src * color / 255`, integer-truncated) applied independently per dot. A single *uniform grayscale* tint (equal R/G/B) scales every dot's luma by the same factor, which mathematically preserves the `luma_i >= avg` comparison exactly — so tinting alone shouldn't move the threshold. Two things break that in practice:

1. **Non-grayscale tints don't scale luma uniformly.** Once a layer is pre-tinted with a genuinely colored value (e.g. `PANEL_GOLD_TINT`/`ICON_AMBER_TINT`, introduced when button icons got real color), a *second*, different-hued tint applied on top does not scale every dot's luma by the same factor, because luma is a weighted sum of channels (`0.299r + 0.587g + 0.114b`) and a colored tint changes each channel by a different ratio. Two dots that started at different hues (one from the icon layer, one from the panel layer, composited into the same mixed cell) can have their *relative* luma ordering shift depending on which tint is layered on next.
2. **Integer truncation compounds across sequential `tint()` calls.** `render_tinted` (`crates/render/src/button.rs`) applies `ICON_CONTRAST_TINT`/`ICON_AMBER_TINT` to the icon layer, composites, then applies the whole `ButtonState` tint on top — two sequential truncating integer multiplies. Small rounding differences between dots whose luma is already close to the cell average can flip which side of the threshold they land on. This is most visible at `Pressed` (the darkest state, `0x8c`): low absolute luma values make a ±1 rounding error proportionally much larger, which is consistent with the observed "everything goes fully solid" result at that state.

Both mechanisms exist because **the same computation (`cell_from_dots`) is asked to decide "is this pixel part of the shape" and "how should mixed-color-and-brightness sub-pixels within one cell be dithered" using post-tint, not pre-tint, data.** Nothing today enforces that a dot's *inclusion* in the glyph mask is decided independently of any tint applied afterward.

## Scope
- Establish and enforce the invariant: **the braille glyph mask (`ch`, which dots are lit) for a given rasterized shape must be identical regardless of any tint(s) subsequently applied to it.** Only the glyph's stored `color` may change with tint.
- Concretely: `cell_from_dots`'s mask decision (`ch`) must be computed from a buffer that never had the offending tint applied, while the displayed `color` is computed from a parallel buffer that does carry the tint — both buffers built from the exact same sprites/placements, so they share identical dot topology (see Decisions below for why this is guaranteed).
- Audit and update every current caller of `dots::tint` (`crates/render/src/button.rs`'s `render_tinted`/`ICON_AMBER_TINT`/`PANEL_GOLD_TINT`, `crates/game/src/scenes/battle_viewer.rs`'s team-tint) to route through this shared mechanism instead of tinting the single buffer that then alone feeds `dots_to_grid`.
- Verify this does not change how genuinely multi-color sprites (the bundled creature GIFs — richly shaded, real photographic-style gradients) currently render. The adaptive-luma dithering itself is not being removed — it still runs once, on the untinted shape buffer — only the *displayed color* now comes from a separately-tinted parallel buffer instead of the same buffer the mask was decided from.

Out of scope:
- Changing `cell_from_dots`'s adaptive-luma algorithm itself (the dithering rule for how a single flat-shaded sprite's sub-cell antialiasing works) — that stays as-is; only *which buffer* it reads luma from changes.
- `27-render-frame-caching`'s frame-to-frame rasterization caching — a related-but-separate performance concern (see that spec; also see `30-asset-decode-caching` for a narrower, distinct performance gap this investigation also surfaced).

## Decisions (v1)
- **New primitive: `dots_to_grid_tinted(shape: &DotBuffer, color: &DotBuffer) -> Grid`.** For each cell, the glyph mask (`ch`) and the visibility/luma-average decision are computed entirely from `shape` (exactly today's `cell_from_dots` rule, unchanged) — `color`'s only role is supplying the RGB values averaged into the output `Cell::Glyph`'s `color` field, for the same bit positions `shape` decided are lit. `dots_to_grid(buf)` becomes the identity case `dots_to_grid_tinted(buf, buf)`, so every existing untinted caller (`draw_board_lines`, roster carousel sprite, `MainHub` logo/title-frame, `DOT_FILLED`/`DOT_UNFILLED` icons) needs no changes at all.
- **Why `shape` and `color` are guaranteed to share identical dot topology:** `tint()` only ever recolors already-`Lit` dots — it never turns a `Lit` dot `Transparent` or vice versa. `composite_dots` picks its per-destination-dot winner using only depth order + Lit/Transparent, never color. So compositing the same placements/depths once from untinted source buffers (`shape`) and once from tinted source buffers (`color`) always yields two `DotBuffer`s with the exact same Lit/Transparent pattern, differing only in the RGB carried by each `Lit` dot. This holds even when multiple differently-tinted sprites (e.g. two teams' pieces) land in the same cell.
- **Compositing (layering multiple sprites/images with depth, e.g. `Button`'s panel+icon, or multiple pieces on the board) still happens at the `DotBuffer` level via the existing `composite_dots` — unchanged.** No new Grid-level compositor is introduced.
- **`Button`'s change is minimal:** `render_tinted` already computes `composed` (the panel+icon composite, pre-`ButtonState`-tint) and `tinted` (post-tint) as separate values. Swap the final `dots_to_grid(&tinted)` for `dots_to_grid_tinted(&composed, &tinted)` — the gold/amber layer-contrast pretints (`PANEL_GOLD_TINT`/`ICON_AMBER_TINT`) still correctly influence `shape` (they establish real compositing structure, not the bug); only the per-state recolor is excluded from the mask decision.
- **`battle_viewer.rs`'s team-tint needs one more step than `Button`**, because each piece carries its *own* tint (not one global recolor applied to the whole board): build `shape` by running `composite_dots` over the raw *untinted* per-piece buffers at today's placements, and `color` by running `composite_dots` over the *tinted* per-piece buffers at the same placements/depths. Then a single `dots_to_grid_tinted(&shape, &color)` call replaces today's single `dots_to_grid(&composed)` call.
- **This is a breaking change to `dots::tint`'s call sites** — every current caller must be updated per the pattern above. Enumerate every call site as part of implementation (known so far: `button.rs::render_tinted`, `battle_viewer.rs`'s team-tint path) and confirm none are missed via a workspace-wide grep before considering this done.
- **Verification requirement**: the same "render across states, diff the glyph mask" technique used to *discover* this bug (render `Idle`/`Hover`/`Pressed` — or team-A/team-B for `battle_viewer.rs` — and assert the `ch` field is identical across all of them at every cell, only `color` may differ) becomes a real regression test, not just a manual check.

- `22-braille-ui-chrome` ✅ — `Button`/`FrameButton`'s `render_tinted` is the primary place this bug was discovered and the primary caller needing updates.
- `18-battle-viewer-baseline` ✅ — `battle_viewer.rs`'s team-tint is another caller needing the same update.
