# Roster Screen — Layout Corrections

## Purpose
`35-roster-screen-stats-abilities-squad` shipped, but the actual rendered result deviates from the original design in six concrete ways the project owner flagged after visually reviewing it. This spec corrects `crates/game/src/scenes/roster_manager.rs`'s layout/rendering to match the original intent — no new mechanics, purely positional/visual fixes to already-shipped code.

**This spec was already attempted once and produced a visibly wrong result** (a details-panel border that filled roughly half the screen and read as a "huge fat" blob instead of a thin frame). Root cause, confirmed by inspecting the diff directly: the attempt stretched the small `FRAME_PANEL` decorative image asset (designed for the Main Hub's compact title box) across the entire, much larger exhaustion+ability rect — stretching an image's painted border ring over a bigger area scales the border's thickness right along with it. That approach is now explicitly forbidden below (see item 3's Decision) in favor of a procedural line, and every "implementation-level, not blocking" judgment call from the first version of this spec has been replaced with a concrete, testable number, specifically so this doesn't repeat.

## Scope
1. **Arrow buttons move to flank the dot row**, not the sprite. Today `arrow_rects` positions the left/right `Button`s vertically centered on the sprite band (`layout().sprite`), reserving `ARROW_W` columns beside it. They must instead sit left/right of `layout().dot_row`, vertically centered on that band — matching the original reference sketch, which shows the arrows flanking the position-indicator dots at the bottom, not beside the creature.
2. **More gap between the dot row's role clusters.** `CLUSTER_GAP` (currently `4`) is too tight — the "Active"/"Bench"/"Reserve" labels visually blend into each other.
3. **A THIN, PROCEDURAL bordered rect around the exhaustion + ability panel** (today: `exhaustion` and `ability_list`, two unbordered rects of plain text sharing the right column, flush against the screen edge). A small margin between the frame and the screen's right edge (not flush), and the exhaustion/ability text inset inside the frame's interior (not overlapping the border itself).
4. **Stat bars: 4 side-by-side horizontal bars, each outlined and labeled, centered above the creature.** Today's `render_stat_bars` draws 4 horizontal-fill bars but stacks them in a vertical column with no labels and no outline, sharing a row with `exhaustion` on the left portion of the screen. The corrected version: the 4 bars (STR/DEX/INT/VIT, `StatKind::ALL` order) sit **side by side in a single row** (not stacked), each with a visible outline/border around its full capacity (so partial vs. full fill is legible) and its stat name labeled directly beneath it — and the whole 4-bar block sits **above the creature sprite**, in the same column as the sprite (not sharing that column with the details panel).
5. **Creature sprite shrunk slightly and shifted right.** Currently large enough that, e.g., Stone Golem's head nearly touches the roster dots below. Inset the sprite's target render size somewhat (still animating, still centered in its own band) and shift its rect right slightly so it reads as comfortably contained within its own space, not crowding neighboring chrome.
6. **Tighten the name→level gap; add a gap between level and the body content instead.** Today there's a visible gap between the name and the level text below it, and NO gap between level and the stat-bar/panel content that follows — the project owner wants this flipped: name and level sit tight together, and the gap goes between level and the body.

Out of scope:
- Any change to the underlying data (`Creature`/`Stats`/`Ability`/`Exhaustion` — `34-creature-attributes-data-model`), the select-and-swap interaction logic, the slide/fade/lerp transition mechanics, or the braille name font (`crate::braille_name`) — all correct as shipped, untouched here.
- Exact pixel-perfect reproduction of the original hand-drawn reference sketch — these are the 6 concrete, itemized corrections the project owner identified; anything not listed here is considered correct as-is.
- `FRAME_PANEL` (`crate::assets`) itself, and its existing use in `MainHub`'s title box — untouched. This spec does not reuse it (see item 3).

## Decisions (v1) — concrete and testable, not implementation-level judgment calls
- **Arrow flanking**: `arrow_rects` is recomputed from `Self::layout(area).dot_row` (the FULL band — dots + role-label row — since `ARROW_H` already matches `DOT_H`) instead of the sprite band, via the same `Anchor::CenterLeft`/`Anchor::CenterRight` + `EDGE_MARGIN` mechanism already used today. The sprite's `layout()` rect no longer reserves `ARROW_W` columns beside it.
- **`CLUSTER_GAP`**: exactly `5` — a MODEST increase from `4` (the project owner asked for "a bit more" spacing, not a dramatic one; `4` was clearing zero columns, the actual defect, so the fix only needs real, positive clearance). This is a confirmed, known-good value: this repo's own code-writer already independently found `5` passes the entire test module clean, including alongside item 1's arrow-flanking layout, at both 40- and 80-col widths. Verified by a test asserting label text from adjacent clusters never occupies the same column at both 40-col and 80-col test widths (the two widths this file's existing tests already use).
- **Details panel width ratio — exact formula, not "centered" or "roughly half":** the screen splits into a LEFT column (stat bars + sprite) of width `area.width * 2 / 3` and a RIGHT column (the details panel: exhaustion + ability list) of width `area.width - (area.width * 2 / 3)` — i.e. a 2:1 split. This must be the literal formula `layout()` uses; a test must assert the details panel's rect width is `area.width - (area.width * 2 / 3)` for at least two different `area.width` values (e.g. 60 and 90 — both cleanly divisible by 3 to avoid rounding ambiguity in the test itself).
- **Details panel border — PROCEDURAL, thin, solid. `FRAME_PANEL` MUST NOT be used for this.** Draw the border directly through the dot pipeline: a `DotBuffer` sized to the panel rect's dot dimensions (`rect.width*2` × `rect.height*4`), with `Dot::Lit(BORDER_COLOR)` set along exactly the outermost dot column on each side (dot-column `0` and dot-column `dot_cols-1`, every row) and the outermost dot row on top/bottom (dot-row `0` and dot-row `dot_rows-1`, every column) — a single continuous 1-dot-thick line per edge, the exact same "pick one dot position and light it across the whole run" technique `battle_viewer.rs::draw_board_lines` already uses for grid lines (reuse that reasoning, not a new algorithm). This produces a thin solid-looking rectangle regardless of how large the panel is, because the border is drawn at a fixed dot-thickness, never scaled by stretching an image. A test must assert: (a) every cell along the panel rect's 4 edges is painted, (b) the panel rect's own INTERIOR (excluding a 1-cell-per-side margin) contains at least one cell that is NOT part of the border glyph pattern (i.e. the border doesn't bleed inward and swallow the whole panel — the actual regression that shipped last time).
- **Right-edge margin**: the details panel rect is inset from `area`'s right edge by `EDGE_MARGIN` cells (the same constant already used for the home button / arrow edge-margins in this file — do not invent a second margin constant).
- **Stat bars layout**: `stat_bar` moves out of sharing a row with `exhaustion` and instead sits directly above `sprite`, spanning the SAME column range as `sprite` (`area.x` to `area.x + area.width*2/3`). Within that rect, the 4 stats divide the WIDTH into 4 equal side-by-side column slices (via `engine_render::stack`, `StackAxis::Horizontal`, mirroring the existing `dot_cluster_rects` pattern in this same file), with `STAT_BAR_GAP` cells between adjacent slices. Each slice: the bottom `STAT_LABEL_H` row(s) render the `StatKind` label as plain text (`STR`/`DEX`/`INT`/`VIT`); the row(s) above that render an outlined bar using the SAME procedural border technique as the details panel (thin, 1-dot-per-edge, via `DotBuffer`/`Dot::Lit` — not an image asset), with the proportional fill (today's `stat_fill_dots`-style logic) drawn as lit interior dots inside that border.
- **Sprite inset and shift — concrete constants, not "an implementation-chosen amount":** add `SPRITE_INSET_LEFT: u16 = 5`, `SPRITE_INSET_RIGHT: u16 = 3`, `SPRITE_INSET_V: u16 = 1` (asymmetric left/right inset is what produces the rightward shift — the render target shrinks by these amounts on each respective side before `fit_dot_dims` is called). A test must assert a real, non-zero gap of fully-blank rows exists between the sprite's lowest painted row and `dot_row`'s top row.
- **Header spacing**: `NAME_H` changes from `3` to `2` (matching the braille name font's actual 2-row glyph height — the extra row was exactly what read as a gap between name and level). A new `HEADER_GAP_H: u16 = 1` row is inserted between `level` and the body content (`stat_bar`/`exhaustion`) — this is where the gap moves to, not removed. A test must assert `level` is vertically adjacent to `name` (no blank row between them) and that a blank row exists between `level` and `stat_bar`.
